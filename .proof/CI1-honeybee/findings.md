# CI1-honeybee: why Honeybee main went red on 6 Nov, and the fix

Session rebuild-ci1h-honeybee-main-green (a9ebc7a8) on metal-1, 2026-11-06. Read-only use of the GitHub API; nothing pushed; `.github` untouched.

## The short version

Two unrelated things happened, and neither is CI-specific.

1. **One line on main makes every bare `send` automation.** Commit 2079e89f "Preserve message sender attribution across input paths" (Tormod, pushed 09:50Z) adds to the daemon's send handler: a sender of `operator` or `human:*` gets `senderKind: "automation"` unless the send carries a humanChat admission from the registered local Apiary service. Automation mail is delivered wrapped in the `[Hive automated message, not typed by a person. ...]` envelope. Every daemon test sends as a bare operator, so from that commit on: the Cell stub no longer sees its `@sh ...` directive at the start of the body (nothing is written in the Cell, nothing is committed, WIP never pushes, the Champion home never gains its secret), the hsr stub echoes the envelope instead of the body (`echo:second`, `echo:hello source`, `echo:after interrupt` never appear), and the tests that assert "a bare operator send is a human turn" assert the old contract. That is 15 test files: actions-rpc, cell-wip, cells, champions, handoff-rpc, human-output-daemon, preflip-verbs, resume-bundles, resume-import, resume-import-bytes, resume-import-cell, resume-reseed, turn-quiet-rpc, turn-trigger-rpc, verbs-cli. The orchestrator's list (cells.1/2/5, cell-wip.1-5, champions.1, handoff.rpc.cell, handoff.rpc.cross-family, human output daemon) is a subset of the same cause. The commit's author had already patched the inline stub agents in spawn-lineage.test.ts to skip the envelope, which is how that one file stayed green.

   It is not CI-only. Reproduced in this Cell on unmodified origin/main (8940403d) with HIVE_TEST_TIME_SCALE=4: turn-trigger.rpc fails with the same `['other','operator'] != ['human','operator']` (`.proof/CI1-honeybee/local/before-turn-trigger-cells.log`). The reason it looked CI-only is that nothing but CI runs the full daemon battery: the landing queue runs only `v2:check`.

2. **The 08:40Z run (a6cd9ad7, D1) failed only `int.3` in integration.test.ts**, "stream contiguous again after refetch". That is a race in the test's own watch consumer, not in D1 and not in the daemon. On a `gap` frame the consumer requests `snapshot` and sets its cursor in the promise's `.then`. RpcClient (v2/cli/src/client.ts, onData/onFrame) dispatches every frame in a socket chunk synchronously and resolves RPC promises through microtasks, so when the snapshot response and the next delta land in the same read, the delta is checked against the stale cursor first, then the `.then` overwrites the cursor with the (now older) snapshot seq, and the following delta is "broken". The daemon side is right: `snapshot` on a watching connection aligns the watch cursor to the snapshot seq (`alignWatch`). The same test passed on the next two pushes, which is what a chunk-boundary race looks like. Not reproduced locally in 15 runs of the original test (`.proof/CI1-honeybee/local/int3-stress-old-vs-new.log`); the fix follows from the client's dispatch order, not from a repro.

Nothing else on main since the last green run (6000b313, 5 Nov 13:20) breaks a test: f1d696c9/a6cd9ad7 (D1) and 3e521e96/8940403d (D3) are clean apart from the int.3 race above. There is no bubblewrap, AppArmor, path or time-scale cause.

## What changed (v2/ only, 8 files, tests and fixtures; no product code)

- `v2/driver-hsr/test-agent/agent.mjs`, `v2/driver-cell/test-agent/agent.mjs`: the stubs read their directives from the body after the automation envelope, the same way the inline agents in spawn-lineage.test.ts already do and the way a real agent reads past the metadata lines. Buz envelopes are untouched (verbs.send-sender still asserts the buz envelope on the peer path).
- `v2/daemon/tests/registered-service-fixture.ts`: `sendHumanChat(client, beeId, body, key)` builds the humanChat admission (sha256 body binding, idempotency key) the way send-attribution.test.ts and human-chat-rpc.test.ts do.
- `v2/daemon/tests/turn-trigger-rpc.test.ts`: rewritten to the landed contract and stronger than before: a bare send, a `senderKind: "human"` label without admission and an explicit automation send all open `other` turns with no human output; after `registerService`, an admitted humanChat send opens a `human` turn whose output is human output, and a later bare send leaves the human cursor where it was; the refusals are unchanged.
- `v2/daemon/tests/human-output-daemon.test.ts`: the two human messages are admitted humanChat sends (the test already registers the service); a labelled-but-unadmitted send is shown to leave `unansweredHumanMessage` null.
- `v2/daemon/tests/turn-quiet-rpc.test.ts`: the daemon is a registered-service daemon and the sends are admitted human chat, because the facts under test (lastHumanOutputAt advancing) are human-output facts; the quiet/endedQuiet assertions are unchanged.
- `v2/cli/tests/verbs-cli.test.ts`: `HIVE_BEE` without `HIVE_BEE_ID` is an unclaimed send (exit 0, sender operator), as the commit's own send-target test asserts; `buz send --sender-human` is refused with "human input requires the authenticated Apiary UI" and enqueues nothing, with or without a bee identity; the session-log check now also asserts the operator delivery carries the automation envelope with `senderKind: "automation"` while the stub's echo is the bare body.
- `v2/daemon/tests/integration.test.ts` int.3: the consumer holds deltas that arrive while a snapshot refetch is pending, applies the snapshot seq, drops held deltas the snapshot already covers and chains the rest; a second gap during a refetch supersedes the first. Same assertions.

Tests whose expectation changed, and why each was wrong under the landed contract: turn-trigger.rpc ("operator stays human"), verbs.send-sender ("missing HIVE_BEE_ID is an error"), verbs.buz ("--sender-human → human:<name>"), human-output-daemon and turn-quiet-rpc ("senderKind: human / a bare send counts as human"). 2079e89f decided that display labels and bare CLI sends never establish human provenance; its own send-attribution.test.ts asserts exactly the behaviour these five tests asserted against. No assertion was dropped without a stronger replacement.

## Verification

Environment: this Cell, origin/main 8940403d plus the change, `npm ci` and `npm run build` with the npm 11 bundled in /opt/node-v24.13.0 (the npm on PATH is 12.0.1 and devEngines refuses it), bwrap 0.9.0 present, HIVE_*/APIARY_* unset via `env -u`, HIVE_TEST_TIME_SCALE=4 and HIVE_BIRTH_CAPTURE_TIMEOUT_MS=4000 as in ci.yml, every run under scripts/with-fixture-warden.mjs.

- `v2:check`: clean. `npm run build`: clean.
- Red to green, the 15 files CI listed, run as one targeted set: 12 of 15 files pass after the change (`.proof/CI1-honeybee/local/after-targeted-15-files.log`); before, turn-trigger-rpc and cells failed as in CI. The remaining three: handoff.rpc.cell and preflip v6.rpc.5 fail only with "Host Git refused: Git >=2.44 is required; found version 2.43.0" (below); champions.1 passed its assertions and timed out once in its 4-second teardown wait for runner hosts, then passed twice in a row when rerun alone (`after-champions-rerun.log`); that teardown wait is unscaled and pre-existing, and CI never reached it.
- `v2:test` (core, 722 tests): green with npm 11 on PATH. With npm 12 on PATH one core test (`release-settle` "deploy archive allowlist") fails because it shells out to `npm pack`; that is this machine, not main.
- `v2:harness`: 14/14 green before and after.
- `v2:driver`: 280/281 before and after; the one failure (execution-handshake "owner completion" timeout) fails identically on the last green commit 6000b313 in a scratch worktree at both time scales, and passed in that commit's green CI run, so it is this host, not main.
- `v2:daemon`, the full battery: 1719 tests, 1645 pass, 67 fail in 20 of 165 files (`.proof/CI1-honeybee/local/after-v2-daemon-full.log`). Every one of the 67 is environmental and fails identically on the unmodified tree (`baseline-nongit-files.log` reruns the six files that are not plainly Cell files): 57 are "Host Git refused: Git >=2.44" across the 14 Cell files plus bee-tmp, confined-peer-rpc, runner-host-artifact, actions-cli, cli.4d and cli/cell-move; delivery-file-read fails because this Cell's tmp base makes the fixture's socket path 107 bytes against the 103-byte limit; helpers-teardown times out at 60 s on this host. None of the 15 files CI listed is among them except the Cell-substrate ones named above.

## What could not be verified here, exactly

- Every Cell-substrate test (cells, cell-wip, actions-rpc, resume-import-cell, handoff.rpc.cell, v6.rpc.5, all of driver-cell in v2:driver2): metal-1 has git 2.43.0 and `v2/core/src/hostGitRuntime.ts` (d22b152a, on main before the last green run) refuses anything below 2.44. GitHub's ubuntu-24.04 image ships a newer git, so CI runs them. No git ≥ 2.44 exists on this machine and installing one is outside the rules. For these files the evidence is: the CI failure is the stub not finding `@sh` after the envelope (the assertions fail exactly where the first `shInCell` result is read, and `actions.rpc.ship` never sees the bee working on its `@sh sleep 2`), and the Cell stub now finds it; the same change is what makes the hsr-substrate siblings (resume-bundles, resume-import, resume-import-bytes, resume-reseed, champions) go green here.
- The int.3 race: not reproduced in 15 local runs of the original test; the fix is argued from client.ts dispatch order.

## Side findings for the orchestrator (not fixed here)

- **Satellites on stock Ubuntu 24.04 cannot run Cells once d22b152a is deployed**: git 2.43 is refused outright. metal-1 is such a satellite (this very Cell runs on a daemon older than that commit). Whoever deploys next should know.
- CI's test step is one `&&` chain, so once `v2:daemon` failed, `v2:driver`, `v2:driver2` and `v2:harness` never ran on any of the three red pushes. C7 in ci/design.md (three parallel jobs) fixes that structurally.
- The daemon test helper's `stop()` waits a fixed 4 s for runner hosts regardless of HIVE_TEST_TIME_SCALE; it bit once here under load.
- execution-handshake.test.ts fails on this host on every commit tried, including the green one. Unowned; not a main regression.
