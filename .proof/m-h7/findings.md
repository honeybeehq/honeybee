# M-H7: `gateway.register` and `skills.install`; Honeybee writes `gateways/apiary.json` itself

Capability tags: **`gateway.register.v1`** and **`skills.install.v1`** (additive; rollout rule 4). Schema v57 (two additive tables, `gateways` and `skill_tree`; CREATE TABLE IF NOT EXISTS, no rebuild). Session: M-H7 worker (netcup-2, Cell `rebuild-m-h7-gateway-skills`), based on origin/main 6a51b3f6 (H6 landed). Apiary is unchanged; nothing in production calls the verbs until C6 and C8.

## What changed (wire)

1. **`gateway.register {name?, url, tokenIssuer?, idempotencyKey?}`** → `{gateway, file, changed, replaced}`. Only the registered local Apiary authority on a direct Unix socket may call it (same gate as `account.lease.grant`: `caller_not_trusted` otherwise, `confined_peer_refused` from a sandboxed Cell). `name` defaults to `apiary` (`^[a-z0-9][a-z0-9_-]{0,63}$`); `url` must be an absolute http(s) URL without credentials, fragment, spaces or control characters, ≤ 2048 chars; `tokenIssuer` is an optional string ≤ 1024 chars. Refusals are `invalid_request` with `details.reason` `name` | `url` | `token_issuer`. Honeybee owns the `gateways` row (name, url, tokenIssuer, principal, registeredAt, updatedAt) and writes `<storeRoot>/gateways/<name>.json` (gatewayRev 2, `transport: "http"`, `writtenBy: "hived"`) at register **and at every daemon boot**, so a pre-C6 Apiary that clobbers the file with its stdio record loses on the next boot. The same registration again is `changed: false` and audits nothing; a changed URL audits `gateway.registered` with the replaced facts. `deployInfo.gateways` lists the rows.
2. **Seeding.** Every home activation (`activateForSpawn`) seeds the registered endpoints as native MCP entries beside the stdio shim files: claude and pi get `"apiary": {"type": "http", "url": …}`, codex and grok `config.toml` get `[mcp_servers.apiary]\nurl = "…"`, opencode gets `{"type": "remote", "url": …, "enabled": true}`. A registered name owns itself: a stdio file of the same name is ignored; other stdio files (e.g. `foundation.json`) keep seeding as before. The gateway activation revision includes the URL, so a populated home converges on its next activation after a re-register. Grok, Kimi and Muse spawn-time `mcpServers` (the adapter's stdio list) do not carry HTTP gateways; those adapters need an HTTP shape in C6 if they are to reach Apiary over W4.
3. **Per-bee token: stopped at the URL.** target.md says the token is "issued at spawn" and lives in apiaryd's `node.sqlite`, but defines no issuer protocol Honeybee could call. `tokenIssuer` is therefore stored and echoed in the file as an opaque string and nothing is minted or forwarded; the seeded entries carry no `headers` / `bearer_token_env_var`. C6 decides whether the token travels in the spawn env (`APIARY_AGENT_TOKEN` is already a forwarded env name for codex) or as a header the seeder renders; either is a small additive change to `gatewayMcpSeed`.
4. **`skills.install {tree: {digest, entries}, idempotencyKey?}`** → `{tree, changed, replaced, homes}`. Same caller gate. Each entry is `{path, sha256, size, executable?, content (base64)}`; `digest` = sha256 over the entries sorted by path, one line each `<sha256> <x|-> <path>\n` (`skillTreeDigest` in `v2/daemon/src/skills.ts`; `readSkillTreeFromDirectory` builds it from a directory). Limits: 10 000 files, 64 MiB, path ≤ 512 chars, relative, no `.`/`..`/empty segments, no `.hive-` prefix. Any mismatch is `invalid_request` with `details.reason` (`digest` | `sha256` | `size` | `path` | `content` | `entries` | `bytes`) and `details.index`, before anything is written. The node keeps its copy under `<dataDir>/skills/<digest>/` (written to a staging dir and renamed; the previous digest's copy is removed after the switch), writes the tree into `<home>/skills/` of every Honeybee-owned account home that exists, and the activation hook installs it into every home activated later (from the node copy, no Apiary round trip). `<home>/skills/.hive-skills.json` records the digest and the files Honeybee owns there: a later tree rewrites changed files, removes files it no longer has, and leaves files it never listed alone. Native (imported) accounts' vendor homes are never written. The same digest again is `changed: false` and audits nothing; a new digest audits `skills.installed`. `deployInfo.skills` carries the current row.
5. **CLI:** `hive gateway register <url> [--name apiary] [--token-issuer s] [--register] [--json]`, `hive gateway list`, `hive skills install <dir> [--register] [--json]`, `hive skills status`.
