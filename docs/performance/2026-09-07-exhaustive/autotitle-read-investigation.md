# Automatic-title scan investigation

This is read-only follow-up work, not an accepted title-behavior change. The real dispatcher runs synchronously during a once-per-second daemon scan. Titled or inactive Bees skip mailbox reads, and an occupied generator slot returns before scanning. Deferred and backoff decisions occur after listMessages, so they do not consume the named eight-probe limit. A 1,000-Bee deferred fleet performs 1,000 mailbox reads each scan. A generate-ready Bee behind it costs 1,001 reads before launch; at the head it costs one.

The [original study](designs/honeybee-autotitle-read-study.md), [harness](designs/honeybee-autotitle-scan-study.mjs) and [counts](evidence/honeybee-autotitle-scan-study.json) preserve the author's report. Its corrections are load-bearing. The scan is one Hz, not the historical five Hz comment. Active untitled does not imply young or small. The 1,000-Bee ramp takes 125 scans and 63,000 reads; 66,000 includes three further steady scans. The stored count artifact abbreviates the per-scan sequence but retains exact totals; the executable harness retains and asserts the sequence in memory. Per-call timing extrapolations in the report are arithmetic, not measured fleet CPU.

[Real-function fidelity checks](designs/honeybee-autotitle-c1c2-fidelity.md) reject the proposed fixed first-k plus SQL count shortcut. Signature count uses nonempty JavaScript-normalized bodies, not row count; arbitrarily many envelope-only rows can precede a substantive message. The bounded shortcut can defer a Bee that the actual code would title. Initial task context uses separately stripped, unclamped text. No approximation is accepted.

A substantive giant mailbox can sustain reads during retry backoff. A genuine deferred giant requires bodies whose normalized content remains empty or a single thin opener; a hand-invented substantive deferred signature is not a state the current defer branch would save. These cases must not be conflated in future fixtures.

A max-id plus row-count probe is a possible change detector under immutable bodies and committed membership changes, but it still scans index entries to count rows. Persistence in the sidecar is unapproved. Restore/import, deletion, version compatibility and stale-cache behavior remain open. A per-dispatcher in-memory alternative should be considered before adding durable fields.

The parent [counterexample](evidence/honeybee-autotitle-uncommitted-counterexample.json) proves that equal max/count alone fails if a cache observes an uncommitted transaction. A speculative id 1 with body A rolls back; a committed send reuses id 1 with body B. AUTOINCREMENT protects previously committed IDs, not rolled-back IDs. Any future contents cache must exclude speculative publication or otherwise prove rollback safety. The fixture's initial createBee return-value setup was corrected before this successful proof; no production failure was involved. CoreStore.inTransaction is an available boundary, but no cache implementation is approved here.

Potential next designs are a committed in-memory change detector, bounded scans with explicit fairness/detection-latency changes, or event-driven invalidation. They need a separate architecture and measurement review. C03's prepared-statement cache is independent and caches no contents.
