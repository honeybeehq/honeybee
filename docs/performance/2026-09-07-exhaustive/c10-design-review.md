# Sparse mailbox history design review

Current main `f468aba8` is clean and includes the accepted pending improvements. This follow-on C10 unit is now accepted with measured tradeoffs; see [results](c10-mailbox-history-results.md). It addresses listMessages, which reads all mail for one Bee in id order and currently scans unrelated mailbox history. Mini measured 3.601 ms CPU for 20 target rows among 100,000 unrelated rows. The callers include the mailbox RPC, automatic title context and the spawn idempotency fallback.

The [frozen real-schema study](designs/honeybee-c10-by-bee-study.md) compared four candidate index shapes plus control. Its [variant data](evidence/honeybee-c10-variants.json) and [initial cascade study](evidence/honeybee-c10-by-bee-study.json) are structural/diagnostic evidence from contended Studio, not acceptance timing. The corrected report SHA-256 is `a4a29e87504ffca36394a05a59025e691bea735466e8dc7e60aeedb6cead1004`; variant data is `aa311dcae545e42a87b783d95a3786cc627e979f21b1425ed4e3c856f1f00913`; initial study is `29573a5946561d839bd38e4bfd26fe333512d15d071165469a2a6b743fb69550`. The author corrected initially reported digests, and the parent independently checked these against file bytes.

A full bee_id index also attracts undeliveredMessages. That pending read then walks and fetches delivered history. The same-Bee negative control with 100,000 delivered rows and 20 pending rows exposed an orders-of-magnitude slowdown. This affects daemon delivery selection and command paths, so the simple full index is rejected. Adding id to the index retains the wrong plan and duplicates the implicit rowid trailer. Adding delivered_at makes pending seeks selective, but forces a full-history sort for listMessages. Neither alternative is accepted.

The selected candidate adds an index on bee_id only for delivered rows. One UNION ALL statement reads pending and delivered partitions and merges them in id order. NULL and non-NULL delivery timestamps partition all rows without overlap. Both branches bind the same Bee; one SQLite statement preserves snapshot and transaction semantics. The delivered-only partial index cannot serve the existing pending predicates. The study shows ordered seeks on both branches, no temporary sort, exact row parity and no adoption by the other mailbox statements.

Production candidate `c25ee08a` and tests `2512bd64` are frozen on `10c25dfc`. Statement caching is deliberately separate; the existing prepare-per-call behavior remains. Mini build, typechecks, 230 core tests and 368 daemon/CLI tests plus one skip passed. Independent ruler review and source-constrained Mini A/A and A/B captures are complete. The required tradeoffs include tiny pending reads over heavy same-Bee delivered history, all-target full-history reads, delivery write CPU, first-open index build, and retained index bytes. Foreign-key cascade speed is not improved by this partial-index design.

Two wording corrections supersede the frozen report without changing its bytes. Post-removal there is one pending mailbox index, not two. Sending a pending row still evaluates the delivered-index predicate, even though it inserts no entry. Zero entry mutation is not a claim of zero CPU cost. The statement matrix includes a test-specific delivered-arm content query; it is not an additional production API.
